# ClaudiniteEngine build plan

Sep 30, 2026 · @Ariel Raunstien

## The plan

Eleven phases, numbered 0 to 10, on three tracks. The chassis (1 to 4) and the pack move (5) run side by side, because neither needs the other until phase 6. Each phase ends on a gate that reads back true from a real repo, never on a judgment call.

0. **Setup and spikes.** Freeze canon growth in Claudinite. Reserve the `@claudinite` npm scope and set up trusted publishing. Create ClaudiniteEngine (private), ClaudinitePacks (public) and ClaudiniteLicenses (private, for the license server alone). Register the Claudinite GitHub App, the R2 bucket and CDN domain, and the license server's Cloudflare resources: its Workers, D1 and the queue, with a Cloudflare token scoped to them held only by ClaudiniteLicenses' deploy workflow. Apply for the Polar account, a step only you can take (business review, identity check, payout bank account). Hold the root and standby root key ceremony. Work through the license design's work notes by hand in a real web session and a real desktop session against a test repo: a background process outlives the web SessionStart hook; a web session sends `repository_dispatch` through the VM proxy with the real user as sender; the web round trip beats the 10-second cut; desktop key latency; behavior on resume; refusal without push access; the path with no App installed; the nightly OIDC App check; per-organization installs; and which account GitHub's 500-an-hour content-creation limit counts against. Also time a Go-plus-Node hook call on Linux, macOS and Windows, and run the Windows launcher under Git Bash. Time the background build of a pack's Go checks at session start, cold and rebuilt, on a macOS and a Windows desktop, which now need Go installed, as the web VM already was.
   - *Gate:* every work note is checked off, the dispatch one returning a check run to a real web session. A failed note changes the license design before any session-start or web-key code is built on it.
1. **Release chassis.** A `cn` that only answers `cn hook session-start` with one hello rule, built for five platforms and published to npm with provenance. The launcher, pin and cache follow the design. The release gate is whatever the release testing design settles. Crash and error reporting ships here, so every later phase has it.
   - *Gate:* a throwaway repo, on a web VM and a desktop, starts a session that shows the hello rule from a pinned, hash-checked binary.
2. **Update chassis.** `cn update engine` with its guards: it skips while main's CI is red and runs the new binary's verify before opening a PR. It also covers CI and auto-merge on the update PR, a deprecation finding for an old file shape, a workflow change filed as an issue carrying the patch, and a revoked release. GitHub starts no CI on a PR opened with the job's own token, so this phase also settles how the update PR's CI is started.
   - *Gate:* the throwaway repo moves v1 to v2 on its own through a merged update PR. A v3 whose verify fails opens no PR and reports what broke, a red main holds the update back, and a revoked release behaves as the design says. This proves that every later fix can reach a member.
3. **Pack chassis.** The ClaudinitePacks release workflow builds each version's vendored set and publishes it twice, to R2 and to the repo's vendored branch, with a signed index. It also covers `cn update packs` with its pre-PR check, and `cn init` reading the vendored branch, all with one hello pack. Its check is written in Go, built in the background at session start, cached until the pack set changes, and run by tag as a child process of cn.
   - *Gate:* a pack version bump in ClaudinitePacks reaches the throwaway repo as a merged pack PR, and a fresh repo adopts from nothing.
4. **License chassis.** Built and deployed from ClaudiniteLicenses: the D1 schema and migrations, the paid key Worker with item grants and the three key paths (web dispatch, desktop `cn login`, Actions OIDC), the public key Worker with no database, the webhook router, the sync Worker as the only writer, and the outside probe. In the binary: session start that never waits (a background key request, the 10-second cut and late recovery), 7-day session keys renewed in the background, the plan read from .claudinite-settings.json, and the per-state gating table applied to stub features. Build the Public plan first, since it needs no billing. Then billing through Polar, in its sandbox: the three seat-based products with monthly and yearly prices and portal seat management, the webhook and API token as sync Worker secrets, the paid key Worker's checkout calls, the sync Worker's signed webhook handler and nightly reconcile, and the checkout link in `cn init`, the seat-refused notice and the overuse issue. Gate: buying, going from 6 to 8 seats, cancelling and a revoke after failed payment each change the key the server issues next. The security review is rerun before this phase ships.
   - *Gate:* a public repo, a Private repo test account and an over-seat account each get the state the license design's table predicts, on a web VM, a desktop and in Actions.
5. **Packs move, early and once.** Split `packs/` into ClaudinitePacks with its history, and freeze `packs/` in Claudinite. The Node engine keeps running members from the frozen tree until they move. Each pack is then ported once, in ClaudinitePacks, by the phase 6 slice that runs its parts: its JS checks are rewritten in Go and its tests are rewritten against the pinned `cn`.
   - *Gate:* ClaudinitePacks holds every pack with its history, and Claudinite's `packs/` accepts no change except an urgent fix, which is made in both places.
6. **Function, one slice at a time.** For each subsystem, write black-box behaviour tests in Go against the command surface. Run them against today's Node engine first, which proves the tests are right, then implement in `cn` until they pass. Slice order: session context and skill mounting; declarative checks; coded checks in Go, where every JS check is migrated, a pack's checks are built in the background at session start and run as a child process of cn, and a run selects checks by tag (work or world, a named pack); the engine's own checks, now in the Claudinite packs, compiled into the engine with the same tags; guards and hook judges, in Go; the task runner and queue; updates and verify; reading today's settings, declarations and local packs in their current shape; `init` and adoption; growth; fleet (sheepdog); the dashboard. Task workers and precondition scripts stay in Node, and the task runner slice gives them their secrets without an unscrubbed environment. Today's tests that check only file shapes or doc text are dropped, not ported.
   - *Gate per slice:* its tests pass on both engines.
   - *Landed so far:* every slice through `init` and adoption (ClaudiniteEngine#55); growth is next.
7. **Packs publish.** Publish every ported pack's first version to R2 and the vendored branch. Canon growth resumes, now writing to ClaudinitePacks. Canon curation moves there too: ClaudinitePacks adopts cn and declares claudinite-canon-curation, whose tasks curate the shelf from its new home.
   - *Gate:* the throwaway repo runs `cn` with the real packs from R2, and the old engine still runs them from the frozen tree.
8. **Website and documentation.** Update the commercial website, ClaudiniteWebsite, for everything the rewrite changed: installing through the launcher and npm, the plans and Polar checkout, the end-user licence and privacy notice, and packs coming from ClaudinitePacks. Write the user-facing documentation, covering adoption, the commands, settings, packs, plans and keys, and the agent-facing documentation a session reads to work with Claudinite, both describing `cn` as phase 6 left it. This phase waits for the command surface to stop moving and runs beside the member moves.
   - *Gate:* a fresh session given only the documentation adopts a new repo, adds a pack and fixes a finding without help, and the website carries no claim the rewrite made false.
9. **Member moves.** A person moves each member in a Claude session that follows a move skill. It adds the launcher and pin, switches the hooks, the `CLAUDE.md` import and the workflows, and removes `.claudinite/shared/`. `cn` then fetches the declared packs afresh from the published versions, and reads the member's settings and local packs as they stand, and verify reports anything left. Reverting the move PR puts the member back on the Node engine. The last Node release files an issue in every member asking for the move, which is the advisory. The move also removes maintenance.delivery, since update PRs auto-merge; lets the repo's open work items drain first; and has the person swap the web environment setup script for the launcher's pre-warm step, or clear it. Dormant repos move first; active repos then move one at a time, each one day after the previous one, once that repo's first nightly update is green.
   - *Gate per member:* its stamp names a `cn` pin, its nightly update PR merged green, and a session there got a key.
10. **Tail.** Since each member's move already removed its Node update task, only Claudinite itself is left: move its open issues, then make Claudinite private and archive it. The old engineVersion stamp stays readable, with a deprecation finding, until `cn`'s next major, as the design allows.
    - *Gate:* every member has moved and the documentation is published. Until then the old update clones Claudinite anonymously, so going private earlier breaks every member not yet moved.

A commercial track runs beside phases 4 to 9 and gates only paid launch, never the migration: Polar approving the account, a privacy notice for the GitHub ids and seat usage kept (with a lawyer reading Polar's terms, which disagree on controller and processor), pricing, and the end-user licence for a closed binary, all of which the website carries from phase 8 on. Bank-transfer and invoice sales, GHE.com, Enterprise Server and GitHub Marketplace stay out of scope. Our own repos run on the Public plan or a comped account until it lands.

This is the plan's shape for your approval. Once you approve it, it becomes a tracking issue with one sub-issue per step, each blocked on the one before, as the repo's migration-plan rules require.
