# Claudinite as an executable: design record

Sep 30, 2026 · @Ariel Raunstien

This is the provenance of the [Claudinite as an executable design](https://claude.ai/code/artifact/0b92671a-39a4-4f36-ac26-8c81f4e9b5eb): every decision and who took it, the research behind each choice, the alternatives not chosen, the security review, and the questions still open. The design itself lives only in that document.

## Decisions and rationale

Every decision taken in the design discussion of 2026-09-30, who took it, and the reasoning and market precedent behind it. The design doc describes the result; this log is the record of why.

| # | Decision | Decided by | Rationale | Market precedent |
| --- | --- | --- | --- | --- |
| 1 | Fold `claudinite-tasks`, `claudinite-growth` and `claudinite-lifecycle` into the engine as part of this change, not before it | Proposed by Claude, asked for by Ariel as a prerequisite; not contested | Moving first costs a fleet-wide workflow edit twice, shims across two update lanes, and moving code the change deletes | None needed; a code-structure call |
| 2 | The engine ships as a closed artifact, not readable JavaScript | Ariel | Protect the engine as the commercial core | Every JavaScript-to-binary packer (Node SEA, `bun --compile`, `deno compile`) keeps extractable source ([Node SEA](https://nodejs.org/api/single-executable-applications.html), [Bun](https://bun.com/docs/bundler/executables)), so only a compiled language meets it |
| 3 | Rewrite the engine in Go | Ariel chose Go or Rust and accepted the code-transition cost; Claude picked Go | Static cross-compiles from one machine, strong subprocess ergonomics; Rust only wins if an in-process JavaScript engine is wanted | esbuild, Pulumi, Terraform and `gh` are Go hosts with plugin or subprocess models ([esbuild plugins](https://esbuild.github.io/plugins/), [Pulumi](https://pulumi-developer-docs.readthedocs.io/latest/docs/architecture/README.html)) |
| 4 | Packs stay Markdown plus `.mjs`; changing their language is a last resort (amended by 36: coded checks and hook judges move to Go) | Ariel | Keep pack authoring cheap and the existing corpus intact | Fast linters moved to Rust or Go while keeping JavaScript plugins in Node beside the native core, as Oxlint does ([Oxlint](https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha)); Ruff, by contrast, refused plugins and rewrote about 900 rules ([Ruff FAQ](https://docs.astral.sh/ruff/faq/)) |

| 36 | All coded checks and hook judges move from JavaScript to Go. Claude chose a child process over in-process loading, Go for hook judges too, and Node kept for task scripts | One compiled executable replaces a Node start per call. | 37 | The root key ceremony runs in a GitHub Actions workflow behind an approval-gated environment instead of on the owner's own machine. ## Research: how tools reach these VMs today

Nothing is installed ahead of time on either kind of VM; every tool arrives at job or session start from a public URL, and the cheap ones ride a runtime that is already there. GitHub-hosted Ubuntu runners ship Node 22 and 24, npm, curl, `gh` and Docker; Homebrew is present but off `PATH` ([runner image README](https://raw.githubusercontent.com/actions/runner-images/main/images/ubuntu/Ubuntu2404-Readme.md)). Every job is a fresh VM, so nothing persists except what `actions/cache` restores ([GitHub docs](https://docs.github.com/en/actions/using-github-hosted-runners/using-github-hosted-runners/about-github-hosted-runners)).

| Channel | How it gets onto the VM | Exact pin | Reads need a token | Verdict for Claudinite |
| --- | --- | --- | --- | --- |
| npm public registry | `npx pkg@1.2.3` or `npm i -g pkg@1.2.3`, riding the preinstalled Node | Yes, plus an SRI hash in a lockfile | No | Primary |
| GitHub Releases | `curl` or `gh release download` of a versioned asset, as uv, bun, deno, gh and ripgrep do ([uv](https://docs.astral.sh/uv/getting-started/installation/), [bun](https://bun.sh/install)) | Yes, by tag URL | No for a public repo; a PAT or App token for a private one ([GITHUB\_TOKEN scope](https://docs.github.com/en/actions/concepts/security/github_token)) | Fallback door |
| Own bucket or CDN with an install script | `curl` of a signed manifest, then the binary, as Claude Code does ([Claude Code setup](https://code.claude.com/docs/en/setup)) | Yes, by version path | Your choice, so it can gate by license | Later, if downloads must be gated |
| Homebrew formula or cask | `brew install`; on Linux runners brew must be put on `PATH` first and is slow; casks are effectively macOS-only ([Homebrew discussion](https://github.com/orgs/Homebrew/discussions/5288)) | Poor: old versions need a versioned formula or a git URL ([brew FAQ](https://docs.brew.sh/FAQ)) | No | Laptop convenience only |
| npm private or GitHub Packages | As npm, with an `.npmrc` token; GitHub Packages wants a token even for public packages ([GitHub docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-npm-registry)) | Yes | Yes, on every VM | Rejected: a secret on every session |
| Container image (GHCR) | `container:` job or `docker run` | Yes, by digest | No for public images | Rejected: wrong unit inside a Claude session |

**How npm itself gets there.** It doesn't: Node and npm are baked into the runner image, and `actions/setup-node` only switches versions, usually from the image's own tool cache ([setup-node](https://github.com/actions/setup-node)). On Claude Code cloud VMs Node and npm are preinstalled too (this VM runs them).

**Native binaries on npm.** npm serves compiled binaries routinely: esbuild, Biome, SWC, Turbo and Claude Code publish one package per platform, marked with `os` and `cpu`, and npm installs only the matching one without an install script ([Sentry write-up](https://sentry.engineering/blog/publishing-binaries-on-npm)). The launcher uses the same packages but fetches the platform one directly, so no `package.json` is needed in a member.

**Packing JavaScript into a binary does not hide it.** Node single-executable apps store the script as-is; `bun build --compile` keeps the full source even with `--bytecode`; `deno compile` embeds the module source; public tools extract all three ([Node SEA](https://nodejs.org/api/single-executable-applications.html), [Bun](https://bun.com/docs/bundler/executables)). Only a rewrite in a compiled language removes the readable source, which is why the engine moves to Go.

**Other package managers.** GitHub runners also carry apt, pip/pipx, cargo, go, gem, conda, vcpkg, NuGet and Composer ([runner image](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md)); this cloud VM has apt, pip, uv, cargo, go, gem, pnpm, yarn and bun, and reaches PyPI, crates.io, the Go proxy, RubyGems, NuGet, GHCR and Docker Hub. None of them gates downloads by license, and none needs to, since the license check is inside the binary.

**Precedent.** Claude Code kept an npm package but made a self-hosted, GPG-signed native installer primary, with `stable` and `latest` channels and exact-version installs ([Claude Code setup](https://code.claude.com/docs/en/setup)). npm stayed as the compatibility door.

## Why this shape, and what was not chosen

Why this shape:

- **Go, not packed JavaScript.** Only a compiled language removes the readable source. Go cross-compiles static binaries for Linux, macOS and Windows from one machine with `CGO_ENABLED=0`, and the closest precedents (esbuild, Pulumi, Terraform, `gh`) are Go. Rust would work too; it would be the pick only if an in-process JavaScript engine were ever wanted.
- **Public npm packages for the binaries.** `registry.npmjs.org` is the one host every target reaches with no setup: it is on the Claude cloud VMs' default allowlist and bypasses their proxy, and it needs no token. A private channel, whether private npm, a private GitHub Release or our own gated CDN, needs a credential on every VM, and a custom domain needs an allowlist entry in every user's cloud environment, a per-user manual step that reliably doesn't happen. GitHub Releases, reachable by pinned tag URL from every VM, is the mirror.
- **License in a signed file, not at the download.** Gating the download protects nothing once one copy exists; a signed license file the binary checks offline keeps the check working on every VM without network access to us (see the licensing section).
- **Our own hash pin, not the registry's word.** The launcher checks the manifest against the hash committed in the member repo, and the binary against the manifest, so a compromised registry alone cannot change what runs. A new version takes effect only through the member's own update PR.
- **Our own launcher, not a package manager client.** `curl` plus a hash check needs no `package.json`, `brew` or `pip` in the member and behaves the same on every VM.

Considered and not chosen: serving binaries from our own Cloudflare R2 behind a licensing Worker. A Claude cloud VM on the default Trusted network reaches `*.r2.cloudflarestorage.com` but not a custom domain ([default allowed domains](https://code.claude.com/docs/en/cloud-environments#default-allowed-domains)), so every user's environment would need our domain added. Cloudflare stays, but only for the licensing Worker, which only Actions and laptops call.

The binary is closed, but the pack SDK is public JavaScript by nature: it is the contract packs are written against, and it contains only the calling side of the protocol. The engine itself stays fully closed: the SDK holds no engine logic, only the message formats and call stubs a pack uses to ask the binary for something, so publishing it reveals nothing of how the engine works.

## Research: engine language and how JavaScript packs keep working

The engine is rewritten in Go; packs stay in JavaScript, and nothing forces the last-resort move of their checks and task workers to another language. This is the pattern Rust and Go linters use when they keep JavaScript plugins, and the one esbuild and Pulumi use for a Go host with JavaScript user code ([esbuild plugins](https://esbuild.github.io/plugins/), [Pulumi architecture](https://pulumi-developer-docs.readthedocs.io/latest/docs/architecture/README.html)).

| What packs contribute | Count today | How the Go engine runs it |
| --- | --- | --- |
| Declarative checks (`declared-checks.json`) | 91 | Natively in Go; no Node involved |
| Coded checks (`worldRules`, `workRules`) | 70 | In a Node child process the binary starts for the call, over a JSON-RPC pipe |
| Task workers and preconditions | 65 | The task itself is a task.json the binary executes; its worker.mjs or precondition script, when it has one, runs as a node process for that step, so a hung one can be killed alone |
| Migrations | 38 | A node process per update run |
| Hook judges | per tool call | A Node process per hook call that has JavaScript judges, exiting with the call; nothing runs between hooks |

**Engine services without imports.** Today 121 pack files import engine modules by relative path, mostly the findings format (83 imports), repo config (77), the pack registry (34) and code scanning (22). Those become a public npm package, `@claudinite/sdk`, that is the only thing a pack imports. Pure helpers, like the findings format, stay plain JavaScript inside it. Anything needing engine state (config, the pack registry, git, GitHub calls with the engine's tokens) becomes a call back to the binary over the same pipe, as esbuild's plugin callbacks do. Node resolves `@claudinite/sdk` to the copy the binary ships, so members need no `node_modules`. The JavaScript runner script and that SDK copy are embedded in the binary and unpacked read-only into the version's cache folder (\~/.cache/claudinite/\<version>/) on first run, so no engine code sits in the member repo; the only Claudinite script there is the launcher, .claudinite/launch.

**What stops working.** A pack reaching past the SDK into engine internals, and anything that shares in-memory state with the engine. Only JSON values cross the pipe. The pipe handshake carries a protocol version, so an SDK and a binary that disagree fail with a clear message.

**The Go rewrite's size.** The engine is about 12,300 lines of JavaScript today, and the three folded packs add about 25,600 more, tests excluded. The folded code is engine code, so it moves to Go with the engine; only packs' own .mjs stays JavaScript. The code-conversions section decides the order.

## Licensing: rationale and limits

Since 2026-10-05 (row 131) only a fleet run checks a license, and a single repository never does; what follows is the rationale of the earlier per-session model, kept as its record.

Never blocking a session on licensing follows JetBrains' degrade-don't-brick model ([JetBrains](https://intellij-support.jetbrains.com/hc/en-us/community/posts/206807935-License-server-How-to-deal-with-offline-clients)); a licensing outage must never read as a broken tool. A customer who stops paying therefore keeps a working repo with everything it accrued (the pinned engine, the committed packs, every rule and skill growth added) but gets no further engine, pack or growth updates. The nightly update keeps trying to renew, so resubscribing resumes updates with no reinstall.

**What this does not stop.** Someone who copies a license file into an unlicensed repo and fakes its remote, or patches the binary. That is the same deterrence level as other offline-licensed tools. Real enforcement is server-side: every license issuance is counted against a subscription, and repos per organization are visible to us.

## Packs: rationale and limits

- **Why per-version archives, not the repo.** Pack versions are per pack while a repo commit is the whole shelf, so serving from the repo could not fetch one pack at one version.
- **Why no gate while packs are open.** Protecting the download of open content buys nothing. If packs close later, the license Worker goes in front of the same bucket with no change to the layout or to members.
- **Why not npm for packs.** npm's dependency resolution duplicates what the engine already does with `requires` and `minEngineVersion`, and it offers no per-pack gate for later.
- **Why only Actions fetches from R2.** The update job has open internet access, so a custom CDN domain costs nothing in allowlists; a Claude Code web VM reaches GitHub but not our CDN, which is why the first adoption session reads the public packs repo instead.
- **Limit of closing the source.** Rules and skills must be plain text on disk for Claude, and `.mjs` stays readable unless moved into Go, so closing packs would gate new versions and browsing, not content a customer already holds.

## Security review

The revised design passed review with eight required changes, now part of the design. The new risks sit where the Go binary meets JavaScript packs, the pipe to the Node processes the binary starts and the GitHub calls packs make through the engine, and in how the license is bound to a repo. Today packs already run inside the engine with every token in reach, so enforcing the new boundary makes Claudinite safer than it is now. Since then the session-long worker was dropped: each call's Node process talks to the binary over its own stdin and stdout, so the findings about the worker's socket, Windows named pipes and stale sockets no longer apply. They stay listed until the review is rerun.

| Severity | Finding | Change adopted into the design |
| --- | --- | --- |
| High | Any local process that reaches the session worker's socket can run pack code and spend the engine's tokens | Socket in a per-session `0700` directory, created under `umask 077`; the peer's user id is checked on every connection; a random session token is required in the handshake |
| High | Windows named pipes are open to other local users by default, and a squatter can take the name first | Explicit access list for the current user only, first-instance flag so a squatter fails, remote clients rejected, plus the handshake token |
| High | A GitHub-call RPC shaped like a raw URL hands any pack every permission the job has | RPC methods are named actions (`openPr`, `createComment`, `readFile`), each pack declares the permissions it needs, the member's settings grant them, and every call is logged with the pack's id; jobs drop `actions: write` unless a task declares it; the Anthropic key never crosses the pipe |
| High | Secrets in the node process's environment are readable by every pack and its child processes | Each node process starts with a scrubbed environment and `NODE_OPTIONS` unset; secrets are read only in Go |
| High | A pack could shadow `@claudinite/sdk` with its own copy | The resolve hook intercepts `@claudinite/*` before normal resolution, refuses anything outside the shipped SDK, and the SDK is hash-checked against the binary; packs containing `node_modules/@claudinite` are refused |
| High | `git remote origin` is attacker-controlled, so a license can be moved to another repo | Licenses bind numeric repo and org ids; in Actions they are checked against `GITHUB_REPOSITORY_ID`, and in Actions the license is fetched at run time rather than read from the committed file; the committed file only serves sessions, where nothing paid runs; every file carries a key id, and the binary embeds at least two public keys for rotation |
| High | The Worker must not trust ids sent by the caller, or accept tokens minted by PR-triggered runs | Ids come only from the token's claims; pinned claims are `iss`, `aud`, `exp`, `nbf`, `repository_id`, `repository_owner_id`, `event_name` (schedule or dispatch only), `ref` (default branch) and `job_workflow_ref`; each token is usable once ([GitHub OIDC hardening](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect)) |
| High | Secrets embedded in a public binary are readable | The binary holds only public keys; CI greps the built binary for secret-shaped strings |
| Medium | Worker or D1 compromise could mint licenses for anyone | Signing key in a Worker secret, never in D1; overlapping keys rotated yearly, the next key shipped one release before use; rate limits per org; alerts for licenses issued to orgs without the App |
| Medium | The Worker becomes an availability dependency | Renew only when fewer than 14 days remain; guards never depend on it; grace of 7 days after expiry |
| Medium | The GitHub App could ask for more than it needs | Metadata read only, no repository permissions, installation events only |
| Medium | Clock rollback or re-committing an old license | The cache keeps the newest issue date seen and refuses older files; beyond that the loss is accepted |
| Medium | Device-flow sign-in leaves a GitHub token on laptops | Only the short-lived license is kept, `0600`; the GitHub token is discarded after exchange |
| Low | Stale sockets, path-length limits, and workers outliving a crashed session | Short socket paths, stale-socket probe and unlink, version and session id in the handshake, 15-minute idle timeout, worker exits when its session process dies |
| Low | A pack sending huge or malformed messages | 16 MiB line cap, per-call timeouts, and the node process is killed on a protocol violation |
| Low | Hash must cover every platform | The manifest lists every platform's hash and the launcher refuses a platform it doesn't list |

Carried over unchanged from the first review, of the earlier Node-tarball version:

- The update PR verifies the GitHub attestation's signing workflow, and npm provenance, before opening; it opens nothing on a miss.
- Publishing uses trusted publishing from one job in a protected environment; the canary job has no permissions or secrets.
- Pins only move forward, above a published minimum, and never to a yanked version; only the update bot may change the pin or the launcher.
- The cache is `0700`, owner-checked, read-only, and re-hashed on every run; the download step in Actions carries no secrets.
- Version and hash strings are validated before use; `curl` is HTTPS-only with a size cap; GitHub Actions are pinned by commit SHA; package names and the `@claudinite` scope are reserved.
- The binary is downloaded raw rather than extracted from a tarball where possible; where a tarball is used, only the one binary is extracted and it is hashed after extraction.

A determined user can still patch the binary or fake a clock; that costs revenue, not safety, and the design deliberately spends nothing more on it.

## Prerequisite: folding tasks, growth and lifecycle into the engine

Fold `claudinite-tasks`, `claudinite-growth` and `claudinite-lifecycle` into the engine as part of this change, not before it. The design assumes from day one that the binary contains them.

Doing it first costs work the executable change would repeat or delete:

| Cost of moving first | Where it shows | Why the executable change removes it |
| --- | --- | --- |
| Every member's scheduler and executor workflows call the tasks pack by literal path, and only a human-merged PR can change them | `packs/claudinite-tasks/stubs/claudinite-scheduler.yml:43`, `claudinite-executor.yml:62`, `src/adopt/converge-workflows.mjs:6` | The executable change repoints those same lines to a `claudinite` command, so both edits land in one fleet-wide PR instead of two |
| The engine and packs ship on separate update lanes, so every moved module needs a shim at its old path | 26 files in other packs import these three by relative path (dashboard, fleet-sheepdog, basics, the site-release tasks, canon-curation) | One binary has one version, so moving source between folders is an internal refactor no member sees |
| Part of lifecycle is the mechanism being replaced | `claudinite-lifecycle/updates/engine-update.mjs`, `install.mjs`, and `bootstrap.mjs:27` | Installing the binary replaces vendoring the engine; that code is deleted rather than moved |

After the fold, the task runner, growth and lifecycle are engine code: a task is a task.json the binary executes, and a task's optional worker.mjs is the only part that runs as an external node process. Whatever in the three packs is content Claude reads (skills, rules prose, provenance files) stays pack-shaped.
